# Gom Jabbar — notes for agent sessions

Installable pain diary PWA (Svelte 5, Vite, Dexie), Italian first, for one Android user. `SPEC.md` is the source of truth for behaviour: update it when behaviour changes. `CHECKLIST.md` is the release steps and the manual phone pass, run right after the deploy: the tester's installed app has the release within seconds, so a merge into `main` is a release.

## Commands
`npm run check` (svelte-check + tsc), `npm test` (vitest), `npm run build`, `npm run size` (150 KB gzipped JS gate), `npm run notices` (the build's `open-source-licences.html` names every package the service worker ships). `nix build` runs all five in the sandbox and leaves the Pages bundle in `result/`; CI does exactly that on every push, a newer push to the same branch cancelling the run before it; a push to `main` also deploys to GitHub Pages, so work on `development` and merge into `main` to release (`CHECKLIST.md` has the steps; never edit `version` in `package.json` by hand, `npm version` does it and tags). The Settings footer shows the `package.json` version, the commit's day and its short hash, baked in by `vite.config.ts` from `GIT_REV` and `GIT_DATE` (set by the flake) or from git. Per-mode values (base path, Google client id, Drive file name) live in `.env.production` (what `vite build` bakes in, `nix build` included: `/` and the production client), `.env.development` (`npm run dev`: `/`, the dev client, `gom-jabbar-dev.json`) and `.env.test` (Vitest: `/`, no client, so no Drive backup); public, committed, see #32. So `npm run preview` serves the production build at `localhost:4173` and Google refuses sign-in on it. Sign-in works on `npm run dev` at `localhost:5173`, on a `vite build --mode development` served by `vite preview --mode development` at `localhost:4173`, and on Pages, at `https://gom-jabbar.618.ovh/`. The dev shell comes from `flake.nix` via direnv (`.envrc`). Dependencies are read from `package-lock.json` by `importNpmLock`, so a lockfile change needs no hash update. `npm test` can print all green and still exit non-zero on unhandled errors: check the exit code, not the summary line. `nix build` only sees files git tracks: `git add` new files before trusting it, or a new test silently does not run.

## Issues
`gh` is in the dev shell, logged in as the repo owner; tool shells do not load direnv, so run it as `nix develop --command gh …`. In issues and other public text, the person using the app is "the tester", they/them, never named or gendered. Labels are `bug`, `enhancement`, `question` (issue types are an organisation feature, unavailable here). Group related work under a parent issue with sub-issues (`addSubIssue`) and record dependencies with `addBlockedBy`, both via `gh api graphql`. An issue that changes behaviour says which `SPEC.md` sections to update.

## Conventions and traps
- Anything handed to Dexie must be a plain object. Svelte `$state` deep proxies cannot be structured-cloned by IndexedDB. Live-query results (`lib/live.svelte.ts`) and objects that flow back to the db use `$state.raw`; form drafts are copied via spreads in `lib/draft.ts`.
- Body region ids (`lib/regions.ts`) are stored in user data. Add regions, never rename or remove them.
- Every i18n key must exist in both `src/i18n/it.json` and `en.json` (a test enforces it). Italian first, terse, informal.
- No confirmation dialogs, with one exception: **Cancella tutto** (`lib/reset.ts`), which has no undo, asks for a typed word. Every other destructive action gets an undo toast (`lib/toast.svelte.ts`).
- Schema change: follow "User data is never lost" below, no exceptions.
- No chart or UI libraries. Charts and the body map are hand-written SVG; colours come from the intensity ramp in `lib/color.ts`.
- jsdom lacks `scrollTo` and `matchMedia`: guard or avoid them in code that runs under tests. `ResizeObserver` (behind `bind:clientWidth`) and `PointerEvent` are stubbed in `src/test/setup.ts`.

## Verifying UI
Screenshot in Pixel 7 emulation with `playwright-core` using the installed Chrome (`chromium.launch({ channel: 'chrome' })`) against `npm run preview`. Block service workers in the context. Seed data through the app's own Settings → Ripristina da file with the output of `node scripts/seed.mjs`. Do not use Chrome's `--screenshot` flag: it hangs and its minimum window width fakes overflow bugs. Playwright download paths have no extension; `saveAs` before opening a downloaded file.

## Tests come first
- Write the failing test before the code: every change in `lib/`, every user-visible behaviour in a screen or component, and every bug fix starts with a test that reproduces it. Red, green, then tidy.
- `npm test` runs with coverage and fails below the thresholds in `vite.config.ts`. They are a ratchet: raise them when coverage grows, and raise them in the same commit that grows coverage. Never lower them, with one exception: a commit that only deletes code together with its tests may lower them to what remains, since fewer covered lines can mean a smaller percentage (#118). `npm run coverage` writes an HTML report to `coverage/`.
- Component tests use Testing Library against the real Dexie on `fake-indexeddb`, not mocks of `lib/`. Screens with no test are debt, not a choice.

## User data is never lost
The app owns the only copy of a person's medical diary. Every schema or export change follows this protocol.

1. **Freeze the version you are leaving, then the one you arrive at.** Before touching `lib/db.ts` or `EXPORT_VERSION`, make sure `src/test/fixtures/db-vN.json` (rows as stored under Dexie version N) and `export-vN.json` (a backup written by export version N) exist and cover every field and edge case: episodes with history, ongoing, full body, several areas, pain 0, custom and disabled vocabulary, a sparse entry, a row with fields no version knows, a row of a dirty shape (no note, no timestamps). Once version N+1 works, add its fixtures too (`db-v(N+1).json`, and `export-v(N+1).json` when the export changed): the guard test wants one for every version up to today's, and they are what the next change is checked against.
2. **Write the transformation down.** Add the N → N+1 rule to `UPGRADES` in `lib/migrations.test.ts`, keyed by export version. A database version that changes only the database (a table, an index) maps to the export version before it in `EXPORT_OF_DATABASE` (`lib/backup.ts`) and needs no rule. That test pushes every fixture of every past version through today's code and requires every field to arrive intact except what the rule says. A version without a fixture fails the guard test. Upgrades and `parseImport` read only frozen rules (`lib/legacy.ts`): copy what a conversion needs there, never import today's helpers into it (`legacy.frozen.test.ts` checks).
3. **Convert, never drop.** An upgrade may delete a field only after writing its replacement. Fields the code does not know about pass through Dexie upgrades and `parseImport` untouched; a test enforces it for import.
4. **Export → import → export is the identity.** The migration test checks it; keep it true.
5. **Dexie upgrades are one transaction.** If an upgrade throws, the database stays at the old version with the data intact. Never catch inside an upgrade function, never write partial results. Every upgrade from version 11 on starts with `await snapshotUpgrade(tx, <version it leaves>)`.
6. `clear()`, `delete()` and bulk overwrites on user tables happen only in `applyImport('replace')`, which snapshots for undo, in the delete paths that already have an undo toast, and in `resetAll` (Cancella tutto), which deletes the whole database behind the typed-word confirmation and nothing else. Nowhere else. Snapshots (`lib/snapshots.ts`) are not user tables: they prune themselves to the newest two of each reason.
7. `parseImport` accepts every export version ever written. `EXPORT_VERSION` is bumped only when the export shape changes.
8. **Fix forward, never roll back.** A bad release is undone by a new release: revert on `development`, then `npm version patch` as usual. Never redeploy an older tag or reset `main`: the phone runs it within seconds, and older code finds a database a newer one has upgraded. Since #113 the app refuses to open one (`lib/db.ts`) and asks for a reload, which would bring back the same old code: the diary stays safe but unusable until the next release. Builds from before #113 open it (Dexie does not refuse it) and write rows of the old shape into it. A backup from a newer version is refused on import (`parseImport`), so that side stays clean.
